# 现有服务器上的 IO 请求命中率测试与控制端对接

本文面向同学已经部署的 Ceph 集群。主机、OSD 数量、安装方式、客户端、
数据目录和缓存容量均以现场核查为准，不要求重建集群、更换客户端或修改缓存预算。
本文是通用执行规范和接口契约，不是一键部署脚本，也不表示已在该服务器上完成测试。

历史实验目录中的专用脚本不能直接套用。不能只替换 IP 就运行其中的初始化、
升级或配置脚本；其他环境的结果也不能作为本机实测结果。

## 1. 先冻结现场环境

执行任何修改命令前，由集群负责人确认并保存以下信息：

| 项目 | 必须记录的现场值 |
|---|---|
| 集群身份 | FSID、CephFS 名称、数据池和元数据池、复制/EC 配置 |
| 服务版本 | OSD/MGR/MON/MDS 的版本与构建 commit，不能只记录管理机 CLI 版本 |
| 目标范围 | 获准测试的 OSD ID 清单、对应主机和设备、其他业务是否共享这些 OSD |
| 执行方式 | 管理客户端的 `ceph` 入口、CephX 身份及配置/密钥文件位置；原生、容器或编排方式 |
| 客户端 | 内核 CephFS 或 ceph-fuse、内核/客户端版本、挂载选项和 I/O 模式 |
| 存储位置 | 已挂载的测试数据目录、工作负载工具目录、结果保存目录、剩余容量 |
| 缓存 | 每 OSD 实际生效的内存目标、自动调节开关、缓存大小及 metadata/KV 比例 |
| 负载 | 仓库 commit、工具版本/哈希、完整配置、数据规模、种子、并发、速率及阶段日程 |
| 初态 | 冷启动、准备数据后状态或明确预热；预热方法、耗时与覆盖范围 |
| 统计协议 | 目标 OSD 清单、采样周期、超时/缺口阈值、阶段边界、标签等待时间和验收规则 |

保留现场原有客户端。例如原来使用内核 CephFS，就先使用内核 CephFS 测试，
不为了得到更高的 Onode 数值而切换到 ceph-fuse。更换客户端必须作为独立实验因素。

保留现场已有缓存配置。`osd_memory_target` 是 OSD 内存目标，
`bluestore_cache_size` 是缓存相关配置，二者都不是 Onode 实际占用；
不能把“4 GiB 内存目标、自动调节”当成“固定 4 GiB Onode 缓存”。
不要照搬其他环境的 8 GiB、metadata 70% 或关闭自动调节等设置。

下面是只读核查命令，在管理员提供的实际 Ceph 命令环境中执行。
容器部署使用现有管理入口，不假定容器名称或宿主机路径；CephX 权限与
本机 sudo 权限是两件事，命令示例不意味着必须授予完整 root 权限。

```sh
ceph -s -f json
ceph versions -f json
ceph osd dump -f json
ceph osd tree -f json
ceph fs status -f json
```

对已确认清单中的每一个 OSD 核查；`OSD_ID` 必须取自该清单，不能固定为 0/1/2：

```sh
ceph tell "osd.${OSD_ID:?请指定获准测试的OSD编号}" onode_cache status -f json
ceph tell "osd.${OSD_ID}" config get osd_memory_target -f json
ceph tell "osd.${OSD_ID}" config get bluestore_cache_autotune -f json
ceph tell "osd.${OSD_ID}" config get bluestore_cache_size -f json
ceph tell "osd.${OSD_ID}" config get bluestore_cache_meta_ratio -f json
ceph tell "osd.${OSD_ID}" config get bluestore_cache_kv_ratio -f json
```

在实际发压客户端执行 `findmnt -T "${DATA_ROOT:?请指定已有测试目录}"`，
核实该目录确实位于目标 CephFS，不能只因目录存在就开始写数据。
若落在本机根文件系统、容量不足、版本/接口不符或 OSD 清单不完整，停止测试。
本流程不格式化 SSD、不创建 OSD、不修改副本数、PG 数或挂载方式。

## 2. 准备并保留负载

1. 使用约定的完整负载和真实工具版本，先生成并校验所有数据，再开始计时测试。
   不擅自缩减为每 case 32 GiB，也不根据节点数临时改变布局或访问分布。
2. 保存配置和模型哈希、文件数量、容量、文件清单及准备日志。
   准备数据可能使缓存变暖，必须记录，不能把准备后的状态称为冷缓存。
3. 每次 case 使用相同的已有数据，不重新 format、不清理数据集。
   工作负载如有写操作，应另定数据快照/恢复和一致性验证方案，不能假定文件内容不变。
4. 使用同学实际使用的 Vdbench 修改版及 SES 版本。若无法取得相同运行时，
   记录替代实现及验证结果，不能声称逐字节复现。
5. 检查实际操作数、配比、阶段是否完整以及退出码。只执行完配置不等于负载分布合格；
   配比容差应提前约定，不能发现偏差后通过放宽阈值或删除记录来宣称通过。

如果当前负载为只读，应用写 IOPS 为零是正常结果，不能将后台写计数冒充应用写流量。
如果需要展示热点迁移和读写变化，应预先冻结满足该需求的新负载版本并完整重测。
固定频率快照不能被描述为保留了真实热点迁移时序。

## 3. 控制端接口

命令需要通过现场已经授权的执行入口调用。下面的“应提供”是控制端适配要求，
不是声明本仓库已经提供了一个支持任意环境的编排器或 REST API。

| 控制端操作 | 已有接口或适配要求 |
|---|---|
| 读取 Onode 状态 | 对固定目标清单逐一执行 `ceph tell osd.ID onode_cache status -f json` |
| 关闭/开启智能缓存 | 对同一清单执行 `onode_cache policy lru/s3fifo -f json`，然后逐一核对状态 |
| 冷热识别状态 | `ceph osd hp status --detail -f json`；检查报告覆盖及新鲜度，不只读取一个百分比 |
| 冷热识别控制 | 专用、全范围测试可用 `ceph osd hp enable/disable`；这是针对所有 up OSD 的控制，不是针对任意子集 |
| 子集冷热控制 | 使用已验证的目标 OSD 本机 admin socket 接口，由管理员提供路由；不能用全局 MGR 开关误操作其他业务 |
| 负载预测控制及准确率 | 使用该模块负责人提供的真实接口、时间戳及指标定义；未提供时标记“未接入”，不能由 Onode/HP 数值代替 |
| 负载启动/结束 | 使用实际客户端和工具入口，返回进程/作业 ID、阶段时刻、退出码和输出位置 |
| 原始采集 | 保存每 OSD 原始响应、请求/响应时间、异常和控制事件，不只保存聚合百分比 |

Onode JSON 字段和错误语义见 [Onode 接口文档](ONODE_CACHE_OPERATIONS.md)。
HP 的 enable/disable 都会完整 reset，包括模型、队列和统计，不能当成保留状态的暂停按钮；
详细契约见 [MGR 冷热识别文档](MGR_HP_OPERATIONS.md)。
MGR 汇总是异步上报，不得把控制请求已发送等同于所有 OSD 已生效。

## 4. 十分钟展示流程

这是同一负载连续运行时的功能展示，不是隔离缓存算法影响的 A/B 实验。
开始前应获得本次切换授权，确认健康状态符合事先约定、后台任务及无关业务可控。
不能默认接受其他测试环境的健康告警白名单。

| 时点 | 操作与检查 |
|---|---|
| 计时前 | 确认数据已就绪；保存现场配置和开关状态；对目标 OSD 设置 LRU 并逐一确认；按各自接口关闭 HP 和负载预测 |
| 0 秒 | 启动正式负载及原始采样，记录真实测量阶段起点，不把进程启动或数据准备时间误作负载起点 |
| 0～180 秒 | 保持 LRU、HP 关闭、负载预测关闭；继续采样。关闭智能缓存不代表关闭所有 Ceph 缓存 |
| 180 秒 | 请求 S3FIFO、HP 和负载预测开启，分别记录请求、成功/失败和实际确认时刻 |
| 确认完成～600 秒 | 保持同一数据和约定负载，实时展示状态、指标及样本量，不重启或重新挂载 |
| 600 秒后 | 停止/完成约定负载，保留计时窗口和完整阶段日程；等待既定 HP 延迟标签窗口并保存终态，再按约定恢复配置 |

计时用控制端单调时钟，跨机器记录使用已同步的墙钟。采样周期可约定为 1～5 秒，
超时与允许的最大缺口在开始前固定。首次完成全清单采样后才能形成有效增量。
跨策略代次变化的区间单列 transition，实际确认晚于 180 秒的部分不能倒算成已开启。

任何控制失败、OSD 重启/增减、缺少目标响应或非预期负载退出都必须记录并使相关
窗口/实验状态失效。不能跳过失败 OSD 后仍显示“全部开启”。是否允许保留其余
有效窗口用于描述性报告，须与整套验收是否有效分开判断。

测试结束先保存 HP 混淆矩阵、队列与丢样情况，再进行 disable/reset。
等待标签的时间不自动扩展 Onode 的正式计时窗口。未排空的样本注明右删失和覆盖率。
恢复 HP 开关也可能清空模型，不能声称能恢复原先模型内存状态；共享集群应事先
明确这一影响。禁止为了“恢复环境”而删除持久化数据或盲目重启服务。

## 5. 指标和界面契约

主指标名称固定为 **IO 请求命中率（Onode 查询口径）**，不是应用数据块命中率：

```text
同一 OSD、同一 cache_instance 的相邻有效样本：
  delta_hits_i   = onode_hits_i(t1) - onode_hits_i(t0)
  delta_misses_i = onode_misses_i(t1) - onode_misses_i(t0)

阶段或集群命中率 =
  sum(delta_hits_i) / sum(delta_hits_i + delta_misses_i) * 100%
```

- 按查询数加权，不能平均 OSD 百分比；分母为零显示 N/A，不填 100%。
- 固定 OSD 集合；实例变化、计数回退、缺样或超长采样间隔必须明确标记。
  缺口不能被静默补值，也不能通过删除低命中窗口提高结果。
- LRU、transition、S3FIFO 独立汇总。显示区间命中率和阶段累计值时，分别标明窗口。
- 以未四舍五入数值判断严格 `>95%`；`>96%` 可作为余量目标，但不能事先保证达标。
  逐 case 通过和总体加权通过不是同一要求，正式规则必须预先约定。
- Onode 计数覆盖目标 OSD 的全部查询，不自动按客户端或 pool 去重过滤。
  MDS、extent-map、数据缓存字节命中率只能作为独立诊断，不能拼接进主指标。
- 冷热准确率用确认覆盖范围内的 TP/FP/TN/FN 计算，另报 precision/recall、
  样本量、覆盖率、丢样和错误；详细接口的零分母占位值不能直接显示成有效准确率。
- 三项功能关闭时，预测/分类准确率显示“未启用/无样本”，不是伪造为 0% 或 100%。
  Onode 的 LRU 基线仍正常显示。
- 读写 IOPS 必须标明来自应用、客户端还是 OSD，不能把大请求拆分后的后端操作数
  当成应用请求数。混合操作单列或说明分类规则。
- 热点迁移图需要真实的对象/区域 ID、时间和热度数据源。只有全局热对象数量或
  分类混淆矩阵不足以绘制空间迁移；该数据源未接入时明确显示缺失，不能用动画替代。

## 6. 容量和算法收益另外验证

若问题是“缓存是否过大、S3FIFO 相比 LRU 提高多少”，应另外进行独立对照：

1. 同一硬件、客户端、负载版本/种子/阶段、数据布局、并发和速率；固定 HP 状态。
   测纯淘汰算法时，不能同时改变客户端、HP、缓存容量和策略。
2. 对每个预先确定的容量档位，分别完整运行 LRU 与 S3FIFO；实际配置一致，
   明确自动调节策略，并采集实际缓存驻留和进程内存，而非只比较配置数字。
3. 每轮采用等价的缓存初态和预热规则，防止第二个算法继承第一个算法的有利状态。
   需要清缓存或重启时必须单独授权；未建立等价初态就不声称是严格算法对照。
4. 安排重复及顺序平衡，保留所有成功/失败轮次；同时报告命中/未命中次数、
   吞吐、延迟、内存和分布偏差。仅有配置内存或 mempool 计数不能冒充 RSS。

如果 LRU 和 S3FIFO 都达到指标，应如实报告；不能为了突出 S3FIFO 而更换统计口径。
其他环境的高命中率不能推出本服务器也通过，更不能证明算法提升幅度。

## 7. 独立复算所需交付

按 case 和 run id 保存并分开输出：

- 环境清单、目标 OSD 列表、实际配置、客户端/服务版本、工具和负载哈希。
- Onode 原始逐 OSD 计数、状态代次、有效/无效区间、分项计数及阈值判定。
- HP 原始状态与混淆矩阵、负载预测原始值/真实值和各自准确率结果。
- 应用及指定层级的 IOPS、热点时间序列、控制事件和确认/失败记录。
- 工具输出、退出码、文件清单、实际访问分布和完整阶段日程。
- 复算脚本与运行命令、逐文件 SHA-256 清单、缺失项和未完成项说明。

代码仓库中的摘要不替代原始证据。结果包应通过双方可访问的存储位置交付，
校验哈希后能独立复算，不能依赖某个作者电脑上的绝对路径。
负载预测或热点数据源未接入时，只能报告已完成的子指标，不能宣称整个指标 1.2 验收通过。
